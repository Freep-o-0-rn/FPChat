# Build 186.1 — замеры загрузки и ошибок медиа

Ветка: `build/186-development`.
База: `build/185-development`, Build 185.1,
`dc916487d2126a288c68637abea2efb7a64dd56a`.

185 остаётся сборкой приближения фото. Серия оптимизации загрузки перенесена
на 186. В этом первом этапе добавлена диагностика; размер истории, порядок
загрузки, лимиты очереди, шифрование, кэширование и жесты не оптимизируются.

## Что измеряется

| Путь | Отметки |
| --- | --- |
| Запуск | Начало встроенного загрузчика; проверка версии; готовность владельцев; регистрация SW; проверка обновления; готовность ядра; ожидания дополнительных слоёв, системного обновления, заявок и затишья ресурсов; снятие экрана подготовки |
| Обычное открытие комнаты | Начало операции; получение ключа; join до заголовков/JSON; подготовка окна истории; начало рендера; первая смонтированная строка; конец текстового рендера; черновик; composer; начальная прокрутка; снятие скрытия списка; следующий видимый кадр |

Новые наблюдения находятся в `FPRuntime169.loading`. Существующие владельцы
вызывают их явно. Нового менеджера, перехвата fetch/таймеров/криптографии,
постоянного хранилища журнала и сервера телеметрии нет.

До загрузки runtime небольшая фиксированная таблица отметок запуска находится
в уже существующем `FPBoot152`. Она не создаёт новой зависимости загрузчика.
Порядок JS/CSS и условия снятия подготовки сохранены.

## Как получить отчёт на телефоне

1. Установить ветку 186 и убедиться, что отображается **Build 186.1**.
2. Полностью закрыть и заново открыть приложение. Открыть проблемный чат,
   дождаться сообщений, открыть фото, попробовать приближение и соседнее фото.
3. Открыть **Настройки → О приложении → Скачать отчёт загрузки**.
   Сохранить `FPChat-186.1-loading.json` как отчёт первого прохода.
4. Нажать **Очистить замеры**. Сразу повторить открытие того же чата/фото
   и сохранить второй отчёт. Метки запуска сохраняются при этой очистке.
5. При сравнении указать устройство, браузер/PWA, тип сети и какой файл
   относится к первому, а какой — к повторному проходу.

Холодный запуск приложения и холодное чтение медиа — разные сценарии.
Для проверки именно холодного медиа можно очистить только кэш медиа через
«Данные и хранилище». Полная очистка данных сайта для этого не нужна.
Тест с пустым Cache Storage не доказывает пустоту HTTP-кэша браузера/прокси.

На iOS нужно физически проверить системный способ сохранения JSON.
Автоматизированно проверено скачивание из Chromium, не Safari/PWA.

## Формат отчёта

- `schema: 1`, `build: "186.1"`, `mode: "passive-owner-hooks"`.
- `boot.points`: миллисекунды от начала навигации. Это абсолютные отметки
  `performance.now()`, а не длительности отдельных этапов.
- `boot.completed`: результат тех ожиданий, для которых существующий код
  возвращает boolean. `false` означает, что условие не выполнено к концу
  ожидания. `system-end`, например, означает завершение ожидания, а не
  доказанный успех запроса: старый код допускает таймаут/ошибку.
- `records`: последние 240 операций. `kind` — `room`, `media`, `viewer`
  либо `gallery-history`. `dropped` показывает вытеснение старых записей.
- `id`/`parent`: только порядковые номера диагностических операций текущей
  страницы. Это не идентификаторы комнат, сообщений, устройств или файлов.
- `startMs`: начало операции от навигации. `points` внутри записи — смещения
  от начала этой операции; `stagesMs` — вычисленные интервалы. `null` означает
  отсутствие обеих нужных отметок, а не нулевое время.
- `durationMs` завершается на `ready` комнаты, окончании чтения/расшифровки
  оригинала или готовности наблюдаемой карточки/слота. Поздние отметки показа
  комнаты могут превышать `durationMs`. Вложенные операции нельзя суммировать
  с родителями как независимые затраты.
- `status`: `pending`, `ok`, `cancelled`, `error`. Незавершённое наблюдение не
  превращается автоматически в ошибку по искусственному таймауту.
- `consumer`: thumbnail в чате, текущий/соседний оригинал галереи либо `other`.
- `cache`: `hit`, `miss`, `expired`, `unavailable`, `error`, `ram-hit`,
  `ram-pending`, `unknown`. `unknown` не означает промах.
- `bytes`: размер прочитанного зашифрованного тела, не размер декодированного
  изображения в памяти. `httpStatus` — числовой HTTP-статус, когда он доступен.
- `counts.pendingThumbnailsAtLayoutWaitEnd`: оставшиеся загрузки при выходе
  из существующего ожидания thumbnails; ненулевое значение помогает увидеть
  срабатывание его временного ограничения.
- `error`: только фиксированная стадия и категория. Отдельно различаются
  HTTP, отмена, транспорт/type error, чтение тела, криптография, ошибка
  изображения/видео и превышение ресурсного лимита. Исходный текст ошибки
  не экспортируется.
- `startupResources`: агрегаты типов ресурсов, начавшихся до снятия boot gate.
  Они основаны на доступном браузерном буфере и ограниченной истории runtime.
  Это частичное покрытие; нулевой `transferSize` не доказывает cache hit.
- `activeElementWatches`: число незавершённых диагностических наблюдений
  элементов. Слушатели удаляются при завершении, отмене, вытеснении и reset.

Чтение дискового кэша входит в `responseAfterAdmission`; это не чистая сетевая
задержка. `queue` изолирует ожидание бюджета. Сравнение `network-start` и
`response-ready` показывает путь получения Response через существующие слои,
но не отдельно SQL, RTT или время внешнего прокси.

## Пределы точности и приватность

Журнал не читает тексты, секреты, recovery-коды, room/device/media/message IDs,
URL или тела запросов. Нет автоматической отправки: JSON создаётся только
после нажатия кнопки. Сам отчёт не включён в старый `FPRuntime.inspect`,
который имеет другой набор полей; для этой проверки нужен именно новый экспорт.

Операции комнат и медиа наблюдаются с момента установки runtime. У прямого
invite-входа запись начинается после уже выполненного join и помечена
`direct-partial`. Если runtime ещё не загружен, отметки не выдумываются.

Общий путь `readEncryptedMedia174` используется также некоторыми голосовыми
и save-операциями: их чтение/расшифровка видны как `other`. Воспроизведение
голоса, сохранение файла и независимые пути I/O целиком не покрываются.

Событие `load` изображения не изолирует длительность нативного декодера.
Для активного видео отмечается `loadeddata`, для соседнего — `loadedmetadata`.
`paint-opportunity` и `visible-frame` обозначают возможность следующей
отрисовки, а не аппаратно измеренный момент появления пикселей. Дополнительный
`decode()` ради диагностики не вызывается. Метрики main thread и сетевых
ресурсов зависят от доступности browser Performance API.

## Предварительное наблюдение по замедлению после 185

В текущей галерее слоты ставятся на загрузку в порядке previous → current → next.
При действующем бюджете один оригинал занимает все четыре слота, поэтому
выбранная картинка может ждать предыдущую. Дополнительно галерея сканирует
страницы истории комнаты. Оба механизма существовали до pinch zoom 185.

Это кандидаты для анализа, не установленная причина ухудшения на телефоне.
В 186.1 они намеренно сохранены; отчёт отделяет соседние загрузки, текущую
картинку и сканирование истории. Также смена версии ассетов делает первый
запуск после обновления отдельным сценарием сравнения.

## Проверки

Среда разработки: Node 24.19.0, Linux Chromium 153, изолированные временные
SQLite/uploads и синтетические зашифрованные WebP. Production-данные не нужны.

Команды:

```sh
npm run test:186:browser
npm run test:186
```

Для локального Chromium вне стандартного Playwright path используется
существующая переменная `BROWSER_EXECUTABLE_PATH`.

Новый suite покрывает 12 групп: порядок boot и room стадий; cold miss/disk hit;
очередь и abort; HTTP/сеть/AES-GCM; body-read; load/ошибка thumbnail; gallery
current/neighbor/RAM/history; unmount cleanup; отсутствие приватных данных;
отключение сбора; ограничение журнала/экспорт/reset; реальный timeout readiness.

Общий gate дополнительно включает проверки 185 (16 групп приближения),
184 (26 reply-сценариев), существующих слоёв/жестов, уведомлений, микрофона,
бюджета медиа и очистки кэша. Для изменённых диагностикой `mountSlot`/`loadAsset`
обновлены только соответствующие source fingerprints старого guard-теста;
проверки поведения и остальные guards сохранены.

Физические iPhone Safari/PWA и Android, а также величина реального замедления
после 185 остаются предметом приёмки. 186.1 не заявляет ускорение загрузки.
Следующий этап выбирается по двум отчётам одного устройства в одинаковой сети.

Для диагностического A/B из консоли доступны:

```js
FPRuntime169.loading.report()
FPRuntime169.loading.reset()
FPRuntime169.loading.setEnabled(false) // очищает операции/слушатели, не кэш медиа
FPRuntime169.loading.setEnabled(true)
```

Отключение относится к новым операциям комнат/медиа. Фиксированные boot marks
и прежняя диагностика Build 169 продолжают существовать.
