# Build 186.2 — лишние превью голосовых и обслуживание кэша

Ветка: `build/186-development`. Основа: 186.1, `5fe5b07`;
приближение фото из 185.1 сохранено.

## Основание

В двух пользовательских отчётах 186.1 каждый показ 100 сообщений запускал
52 запроса audio/thumb с ответом 404 и шесть запросов фотопревью.
Все шесть фотопревью были в Cache Storage, но отдельные операции доступа
к кэшу занимали почти 12 секунд. Отчёты не разделяли caches.open,
localStorage/JSON и Cache.match. Поэтому утверждать, что именно обходы
метаданных вызвали все 12 секунд, пока нельзя.

## Изменения и владельцы

- `app.js`: существующий renderer пропускает загрузку картинки для audio
  до создания диагностической записи, увеличения счётчика и входа в очередь.
  `voice.js` по-прежнему создаёт плеер, получает waveform metadata и загружает
  оригинал при воспроизведении. Запросы voice-meta не являются thumbnails.
- `storage167-cache-fix.js`: изменённые метаданные собираются в один проход
  после 100 мс без новых изменений. Повтор тех же метаданных проход не запускает.
  Одновременно выполняется только один repair; изменения во время ожидания
  Cache Storage обрабатываются последующим проходом. Явный `repair()` возвращает
  общую Promise до завершения этих проходов. Ранее известные размеры не теряются,
  если следующий ответ истории не содержит размеров превью.
- Обход проверяет существующий clear guard после асинхронных операций.
  Он обновляет только метаданные; физические Cache.put/delete по-прежнему
  проходят через `FPNetwork171`. Нового менеджера и нового пространства кэша нет.
- `storage167.js` и `FPRuntime169.loading`: явные отметки внутренних стадий
  чтения кэша и фонового repair. Никаких дополнительных запросов или сканирований
  ради диагностики нет.

Размер истории остаётся 100, бюджет медиа и ожидание начальной геометрии
остаются прежними. Снятие скрытия текста до готовности медиа — отдельный этап,
так как оно требует проверки позиции прокрутки и непрочитанных сообщений.

## Новые поля JSON

Экспорт: `FPChat-186.2-loading.json`, `schema: 1`. Изменения схемы аддитивные.

| `stagesMs` | Измеряемый интервал |
| --- | --- |
| `cacheOpen` | Ожидание существующего `caches.open` |
| `cacheMeta` | Чтение/разбор метаданных; при загрузке медиа также проверка срока хранения |
| `cacheMatch` | Ожидание `Cache.match` |
| `cacheDelete` | Удаление просроченной записи и обновление её метаданных |
| `cacheKeys` | Получение списка записей при repair |
| `cacheRepair` | Обход полученного списка, исправление метаданных и синхронное уведомление |

`cacheOpen`/`cacheMeta`/`cacheMatch`/`cacheDelete` входят в общий `cache`;
их нельзя прибавлять к нему как независимые затраты. `null` означает, что
не хватает отметок завершённого интервала, а не нулевую длительность.

`kind: "cache-repair"` — отдельная операция обслуживания с
`counts.entries` (длина списка кэша) и `counts.updatedEntries` (исправленные записи).
При ошибке стадия `cache-repair`; исходный текст исключения не экспортируется.
Пропущенный до начала проход не создаёт запись; прерванный после старта
из-за очистки помечается `cancelled`. Счётчики относятся к журналу последних
240 операций: при `dropped > 0` они не описывают всю сессию.

Отчёт по-прежнему не содержит текстов, секретов, URL или идентификаторов медиа.
Отключение диагностики не отключает batching и исправление audio/thumb.

## Проверка

`npm run test:186:media-cache` проверяет девять групп в изолированном Chromium:

1. Рендер 100 сообщений: 52 плеера голоса, шесть изображений, ноль audio/thumb,
   один отложенный проход обслуживания.
2. Повторный рендер: шесть попаданий в зашифрованный кэш, без сетевых
   запросов превью и без повторного repair неизменившихся метаданных.
3. Настоящее воспроизведение тестового зашифрованного WAV по запросу.
4. Превью видео и его значок.
5. Объединение разнесённых по времени обновлений и восстановление категорий
   старых записей кэша.
6. Один выполняющийся repair и последующий проход для поздно добавленной записи.
7. Пропуск записи метаданных, если во время ожидания начинается очистка.
8. Разделение искусственно задержанных open и match в диагностике.
9. Ошибка repair, освобождение задачи, успешный повтор и приватность отчёта.

`npm run test:186` дополнительно запускает диагностику 186.1, проверки 185/184,
бюджета медиа, владельца кэша и его очистки. Это функциональные проверки Linux
Chromium, а не замер ускорения физического iPhone или Android.

В тесте 185 ожидание ответа галереи переведено на общую Promise для всех
перехваченных ответов истории: параллельный фоновый запрос больше не может
перезаписать единственную функцию освобождения ответа. Проверки сохранения
элемента под пальцами и всех 16 групп приближения сохранены.

## Приёмка на телефоне

1. Обновить ветку 186, проверить надпись **Build 186.2**.
2. Сохранить существующий медиакэш. После нового запуска открыть тот же чат,
   дождаться превью, проверить голос, фото, приближение и reply.
3. В **Настройки → О приложении** скачать отчёт загрузки.
4. Очистить только замеры, повторно открыть тот же чат и скачать второй отчёт.

Ожидаемый результат: нет операций `chat-thumbnail` с `mediaType: "audio"`;
меньше очереди превью; повторный рендер неизменившихся данных не запускает repair.
Если превью снова задержатся, новые поля покажут, какой внутренний этап кэша
занял время. Ускорение на телефоне оценивается только по новым отчётам.
Перезапуск приложения и холодный медиакэш — разные условия: очистка замеров
и обычный перезапуск не удаляют сохранённые превью.
