## Статус и границы

Код 174 реализован, автоматическая проверка 169–174 и две браузерные регрессии пройдены. Переход к 174 и публикация отдельной ветки выполнены по прямому указанию пользователя после доработки 173. Ручная приёмка на слабом Android и iPhone PWA и полный baseline физических устройств остаются открытыми. Поэтому исходный критерий «задержки уменьшаются на слабом устройстве» ещё не объявляется выполненным. Build 175 не начата.

Соблюдён принцип из конца CHANGELOG: изменения встраиваются в существующие механики и владельцев. Серверные API/SQL, шифрование, retry/clientMessageId и формат persistent storage не менялись. Новая persistent queue не создаётся.

## Что изменено

1. `renderChats` сохраняет строки по roomId, обновляет только изменившуюся разметку, переставляет существующие строки и объединяет быстрые повторные запросы. Обработчики click/long-press остаются у той же строки. Поиск отменяет устаревший проход.
2. `FPWork174` обрабатывает создание/удаление строк и историю порциями: до 100 элементов или около 6 мс между проверками. Между порциями отдаёт управление браузеру; async-элементы выполняются последовательно. Это мягкий бюджет между элементами, не гарантия максимальной длительности отдельного элемента. `maxSliceMs` включает время ожидания async, это не чистое CPU-время.
3. Критические startup-зависимости описаны в `startupDependencies174` в `index.html`. Preload переносит загрузку части ресурсов вперёд, но не меняет порядок исполнения. Карта охватывает изменённые критические цепочки, не является полным графом всех исторических модулей.
4. `FPHistory174` загружает окно около anchor двумя существующими запросами `before/after`, поддерживает движение в обе стороны и выгружает дальние DOM-узлы. Переходы reply, pins, unread и к концу используют тот же путь. Устаревшие страницы и смена комнаты отменяются/игнорируются.
5. Выгрузка DOM не удаляет каноническое сообщение или выделенные id. Read/status сохраняются в MessageStore; старые страницы не отменяют edit/delete. Новый incoming при чтении старой истории учитывается без добавления узла через разрыв истории. Отправка из старой истории сохраняет optimistic node и возвращает к концу без дублирования ACK.
6. Исправлены ранняя установка unread divider при порционной отрисовке, оставшийся разделитель выгруженного anchor и переход к первому непрочитанному вне окна. Cursor продвигается даже через страницу, все записи которой уже tombstones. Поздний thumbnail освобождает URL вместо привязки к удалённому узлу.

## Владельцы и ограничения окна

| Ресурс | Владелец / поведение |
|---|---|
| Room/key/generation/cancel | Существующий `FPRoomContext170`; запрос окна дополнительно отменяет предыдущую навигацию того же окна |
| Fetch/XHR, media/cache | Существующий `FPNetwork171`; история использует его глобальный fetch, второго транспорта или cache writer нет |
| Канонические данные, reply, статусы | `FPMessageStore172`; DOM не становится вторым хранилищем |
| Scroll/viewport/gesture/layers/DOM events | `FPScroll173`, `FPViewport173`, `FPGesture135`, `FPLayer173`, `FPDOM173`; история пишет scroll через существующего владельца |
| Рабочий диапазон истории | `FPHistory174`: page 100, обычное установившееся окно до 300 сообщений |
| Диагностика | `FPHistory174.snapshot()`, `FPChatList174.snapshot()`, `FPWork174.snapshot()`; coverage `FPRuntime` остаётся частичным |

Страница сначала рендерится отдельно, затем монтируется и обрезается; во время операции может существовать ещё до 100 узлов (при замене anchor — отдельное окно до 200). Видимые узлы и неподтверждённые отправки принудительно не удаляются, поэтому 300 — рабочий предел истории, не абсолютный предел всего DOM или очереди отправки. Нет скрытого неограниченного кэша отсоединённых DOM-деревьев. Политики размера канонического MessageStore остаются прежними.

При отказе загрузки `history174.js` включается существующая legacy history: клиент доступен, ошибка отражается в `FPBoot152.errors()`, но bounded DOM в этом аварийном режиме не обещается. При отказе `work174.js` используется последовательный fallback без гарантии порционного yield. Эти пути не работают параллельно с новым владельцем в штатном режиме.

Startup-ускорение отдельно не заявляется: разница baseline ниже слишком мала для такого вывода.

Три независимых браузерных профиля на вариант; сравнение проводится последовательно, без параллельного браузерного regression runner. ## Регрессия

`npm run check:169-174`: все шесть наборов PASS. Сохранены VM/static проверки 169–173; 174 дополнительно исполняет отменяемые последовательные порции, проверяет распространение ошибок, отсутствие циклов в startup map и синтаксис public/inline JS. Это не замена браузерному UX-тесту.

`npm run test:173:browser`: **17 PASS, 0 FAIL**, прежняя совместная регрессия 169–173. Искусственная задержка anchor теперь распознаёт и старый курсор, и новый запрос около anchor; сами утверждения о позднем результате сохранены.

`npm run test:174:browser`: **17 PASS, 0 FAIL**:

1. Сохранение строк, точечное обновление и отмена устаревшего поиска.
2. Yield и отмена порции.
3. Далёкий сохранённый anchor: два запроса, offset с допуском 2 px.
4. Шесть страниц назад и шесть вперёд: variable-height сообщения, предел 300, дрейф anchor до 2 px.
5. Reply после выгрузки, canonical edit и tombstone.
6. Реальный server pin и переход к далёкому сообщению.
7. Выделение после выгрузки/возврата и удаление offscreen сообщения через API.
8. Отправка из старой истории, один подтверждённый узел и переход к концу.
9. Продвижение через полностью tombstoned страницу.
10. Поздняя anchor-загрузка A не меняет B.
11. Первое непрочитанное далеко от конца видно; скрытый хвост не становится read.
12. Кнопка unread загружает отсутствующий в DOM первый unread; нет orphan divider.

14. Thumbnail после выгрузки освобождает URL и не возвращает его в старый узел.
15. Задержанный room-lifecycle при старте и по одной копии владельцев.

В fixtures: 1500 собственных сообщений разной высоты, короткая комната и 1200 входящих с первыми 200 прочитанными. Incoming race и thumbnail race управляемые; последний не заменяет тест реальной загрузки фото. Ограничения 173 по реальным upload/progress/cancel, voice/microphone/autoplay, push, background/foreground и физическим жестам/клавиатуре сохраняются. Длительная память всего процесса не измерялась.

### Команды

Нужны установленные серверные зависимости, Playwright и Chromium. Серверный Node должен быть совместим с native `better-sqlite3`. В отдельной среде пути задаются через `NODE_PATH`, `FPCHAT_TEST_NODE`, `BROWSER_EXECUTABLE_PATH`; при обычной установке используется текущий Node и Chromium Playwright.

```sh
npm run check:169-174
npm run test:173:browser
npm run test:174:browser
FPCHAT_BENCH_OUTPUT=/tmp/list174.json npm run bench:174:list
FPCHAT_BENCH_OUTPUT=/tmp/history174.json npm run bench:174:history
```

Для сравнения неизменённой 173 создать отдельный checkout и запускать те же benchmark scripts из 174:

```sh
git worktree add --detach /tmp/fpchat-173 860e303f16af8eafbf7526953d262e481d037d2f
FPCHAT_TEST_ROOT=/tmp/fpchat-173 FPCHAT_BENCH_OUTPUT=/tmp/list173.json npm run bench:174:list
FPCHAT_TEST_ROOT=/tmp/fpchat-173 FPCHAT_BENCH_OUTPUT=/tmp/history173.json npm run bench:174:history
```

Benchmark scripts запускают реальный сервер на свободном локальном порту, используют только свою временную SQLite, закрывают процессы и удаляют fixture. Рабочая БД и push-подписки не используются. В обоих checkout должны быть доступны серверные зависимости, в том числе через общий `NODE_PATH`.

## Откат

174 не содержит миграций БД и изменений форматов очереди/кэша. Точка возврата — вся ревизия 173 `860e303f16af8eafbf7526953d262e481d037d2f`, а не отдельное удаление `history174.js`.

Для локального стенда остановить процесс, переключить чистый checkout на эту ревизию (`git switch --detach 860e303f16af8eafbf7526953d262e481d037d2f`) и запустить штатным `npm start`. `version.json` вернёт suffix 173; затем полностью перезапустить клиент и проверить version, отправку и открытие anchor. На общей ветке делать обычный revert коммита 174, без переписывания истории. `update.bat` в этой сборке меняет только номер banner; логика updater/startup относится к 175 и здесь не переделывается.
