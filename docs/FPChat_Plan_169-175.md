# FPChat — план оптимизации Build 169–175

Статус: зафиксированный план разработки.
База: стабильная Build 168 (`9c53a7a0329f267a51c7e976f1c4c825d9b7ae42`).
Ветка разработки Build 169: `build/169-development`.

Текущая работа: доработка `build/173-development` по [аудиту 169–173 от 19.09.2026](FPChat_Audit_169-173.md). Автоматическая регрессия пройдена; baseline устройств и ручная приёмка 173 остаются открытыми. 174 не начата.

## Общее правило

Пользовательская механика FPChat не меняется без отдельного решения. Отправка, медиа, voice, unread, статусы, presence, typing, свайпы, long-press, lazy history, восстановление позиции, блокировки, invite и recovery должны сохранять текущее поведение.

Новый владелец считается внедрённым только после подтверждения, что старый механизм больше не выполняет ту же работу независимо. Старое имя функции или временный адаптер допустимы, если они не хранят и не изменяют собственное каноническое состояние.

## Build 169 — диагностика и проверочная база

- FPRuntime в режиме наблюдения.
- Метрики запуска, открытия комнаты, восстановления соединения, завершённых сетевых ресурсов, long tasks, размера DOM и доступной браузеру памяти.
- Явное указание покрытия: неподсчитанные таймеры/наблюдатели не показываются как ноль.
- Карта известных владельцев и технического долга.
- На серверной стороне — безопасные измерения задержек, памяти и горячих DB-путей без публикации приватных данных.
- Фиксация воспроизводимых регрессионных сценариев.

Готовность: есть baseline Build 168/169, карта владельцев, понятное покрытие диагностики и повторяемые проверки.

## Build 170 — RoomContext, Lifecycle и WebSocket

- Каждая критичная async-операция получает room context: room, key, generation, AbortSignal.
- После await проверяется актуальность контекста.
- Уже начатая отправка/upload не отменяется только из-за ухода с экрана: для неё отдельный operation context.
- Единый lifecycle приложения: foreground/background, online/offline, room/view changes.
- Развитие существующего владельца WS, устранение параллельного управления соединением.
- Постепенная замена 500 мс polling на события.
- Дедупликация reconnect/resume sync, активная комната имеет приоритет.

Готовность: запоздалый ответ комнаты A не меняет B; ключи не смешиваются; WS имеет одного владельца; переходы не накапливают задачи/подписки.

## Build 171 — сеть, кэш и память медиа

Контрольные этапы:
1. FPNetwork для request/fetch.
2. Перенос старых fetch wrappers в явные обработчики.
3. Единый upload API поверх XHR с сохранением progress/cancel/error semantics.
4. Один владелец записи/очистки Cache Storage.
5. Media resource policy: лимиты параллелизма, cleanup Blob/ObjectURL, voice/media cleanup.

Готовность: старый кэш читается; запись и очистка имеют одного владельца; очистившийся кэш не заполняется старой задачей; длительное использование медиа не даёт неограниченного роста памяти.

## Build 172 — MessageStore, reply и правила объединения

- Каноническое состояние сообщений: id/clientMessageId/status/edit/delete/reply/media metadata.
- Правила merge: старая история не отменяет новое редактирование, не восстанавливает deleted и не понижает read/delivered state.
- Reply states: missing/loading/loaded/deleted/unavailable.
- Появление/изменение исходного сообщения инвалидирует и обновляет зависимые reply-preview.
- Сохраняются текущие clientMessageId и reconnect/retry semantics.
- Новая сохраняемая offline-очередь в обязательный объём 172 не входит.

Готовность: состояние согласовано после reload/reconnect; reply корректно обновляется; старые async-данные не побеждают новые.

## Build 173 — Layer/Gesture/Scroll/Viewport

- Развивается существующий `FPGesture135`, второй независимый GestureManager не создаётся.
- LayerManager хранит явный стек активных слоёв.
- ScrollCoordinator/Viewport получают однозначное владение геометрией, клавиатурой и scroll state.
- DOM decorators постепенно переходят на явные lifecycle/mount events.
- Сокращаются DOM scans в горячем touch/pointer path.

Готовность: фото, меню, выделение, voice и chat не перехватывают чужие действия; клавиатура не ломает расположение; одним свойством геометрии не управляют несколько независимых механизмов.

## Build 174 — слабые устройства и длинная история

Последовательность:
1. Точечное обновление списка чатов.
2. Сокращение повторной работы, большие наборы обрабатываются порциями.
3. Повторные замеры.
4. Startup-оптимизация только после карты зависимостей скриптов.
5. Подготовка загрузки истории около anchor.
6. Bounded message DOM с проверкой unread/reply/pins/selection/media/scroll restore.

Готовность: длинная переписка не увеличивает DOM без ограничения; scroll/anchor сохраняется; измеренные задержки уменьшаются на слабом устройстве.

## Build 175 — сервер, БД и обновление

Каждый этап — отдельный commit, проверка и точка возврата.

### 175.1 — явная серверная композиция
Убрать runtime textual patching `server.js`, сохранить API/WS/DB semantics.

### 175.2 — media I/O
Temp-file/streaming encrypted upload, лимиты ресурсов, interrupted upload cleanup, повторная проверка room state перед финальным commit.

### 175.3 — SQL
Убрать подтверждённые N+1, batch hot paths, индексы только после `EXPLAIN QUERY PLAN`.

### 175.4 — blocks
Event-driven уведомления после успешной DB transaction вместо полного snapshot polling.

### 175.5 — updater/start launcher
`update.bat` только обновляет. `start_chat.bat` отвечает за запуск одной актуальной копии сервера. Проверяются backup/restore.

После 175.1–175.5 проводится отдельная совместная проверка всей Build 175.

### Финальное интеграционное правило Build 175

Build 175 — финальная точка всей серии 169–175, а не отдельная серверная оптимизация.

К её завершению обязаны одновременно оставаться действующими владельцы и инварианты предыдущих сборок:

- Build 169 — `FPRuntime`, baseline/coverage и проверочная база;
- Build 170 — RoomContext/generation/cancellation, Lifecycle и единственный Connection/WS owner;
- Build 171 — `FPNetwork`, XHR/upload, media/cache ownership и resource policy;
- Build 172 — `FPMessageStore172`, reply dependencies и merge rules;
- Build 173 — Layer/Gesture/Scroll/Viewport/DOM lifecycle ownership;
- Build 174 — performance/bounded DOM/anchor/startup изменения после их приёмки;
- Build 175 — server composition/media I/O/SQL/blocks/updater.

Ни один этап 175 не имеет права обходить или создавать параллельного владельца поверх механизмов 169–174.

После отдельных проверок 175.1–175.5 выполняется **общий owner audit и полная регрессия всей цепочки 169–175**. Финальная 175 считается готовой только если:

1. новые владельцы предыдущих сборок всё ещё являются единственными владельцами своих ресурсов;
2. compatibility fallback не выполняет ту же работу независимо на нормальном пути;
3. клиент и сервер совместно проходят критические сценарии;
4. обновление/откат воспроизводимы;
5. `main` переводится на 175 только отдельным явным решением после итоговой проверки.

## Обязательные регрессии для каждой сборки

- Быстрые A → B → A с искусственно задержанными ответами.
- Потеря соединения до/после server ack.
- PWA background/foreground и повторный запуск браузера.
- Text/reply/edit/delete/reactions/unread/checkmarks/typing/presence.
- Block/unblock/invite/system chat/recovery.
- Photo/video/file/voice, media cache и очистка во время загрузки.
- Длинная история, первое непрочитанное далеко от конца, reply jump, pins и selection.
- Реальные ПК, слабый Android и iPhone PWA.

## Критерий завершения миграции владельца

- Сеть: согласованный путь; старые самостоятельные wrappers больше не управляют запросами.
- WS: нет старых polling/handlers, создающих параллельное управление.
- Messages: изменяемое каноническое состояние только в MessageStore.
- Cache: запись и очистка имеют одного владельца.
- UI geometry/input: одним действием/свойством не управляют несколько независимых механизмов.
